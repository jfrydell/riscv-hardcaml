# Project Basics

This project aims to implement a RISC-V CPU in Hardcaml.

The project is built with the dune build system and uses opam for package management.
To build in the correct environment, use `opam exec -- dune build`.

## Running / Testing

All tests, primarily several configurations of fuzzing tests, can be run with `opam exec -- dune runtest`.
If a test fails, it can be reproduced and debugged with the `bin/main.ml` executable's `debug` command, using `opam exec -- dune exec riscvhardcaml -- debug <ARGS>`.
This supports the following arguments:
- Exactly one of `--basic-test T` or `--fuzz-test CONFIG --seed S --insn-count N` must be provided, where `T` is the test number (always 0 for now) and `CONFIG` is one of "small", "hazards", or "coverage" (based on the suite of fuzzing tests that failed).
- `--emulator-trace INFO` and `--trace INFO` print per-emulator-step (known-good) or per-simulated-cycle state, where `INFO` is a comma-separated list of register numbers `0`-`31`, `pc`, and `insn`.
- `--max-cycles N` stops simulation if the requested instruction count has not committed in the given number of cycles.
- `--view-waves` opens an interactive waveform viewer for human viewing, and should not be used by text-based agents.

# Hardcaml Style Guide

This document describes the preferred style for clean Hardcaml implementations in this repository.

## Goals

The main priorities are:

- Make the hardware behavior easy to read from the source.
- Prefer structure that matches the underlying control/dataflow, rather than software-style incremental mutation.
- Keep the final implementation compact, but not at the cost of obscuring important sequencing or dependencies.
- Use intermediate exploratory implementations when useful, then simplify the final version aggressively.

A messier draft can be a good design tool. Extra wires, explicit state signals, or more verbose control logic may help clarify what must happen. Once the behavior is understood, the final checked-in version should usually be simplified.

## Signal Declaration Style

- Prefer `let%hw name = ...` for named signals.
- Use `Types.Clocking.reg` for registers.
- Avoid old `Reg_spec`-style APIs in new code.
- Use record helpers generated by `[@@deriving hardcaml]`, such as `My_struct.Of_signal.mux2` or `My_struct.map`.

Example:

```ocaml
let%hw next_pc = wire 32 in
let%hw pc_reg = Types.Clocking.reg i.clocking ~enable:~:(stall F) next_pc in
```

## When To Use `wire`

Use `wire` only when it is actually needed.

Good reasons to use a wire:

- To break a cycle.
- To refer to a signal before its final value can be defined because of declaration order.
- To connect RAM outputs after RAM instantiation when the signal is consumed earlier.

Do not use a wire just to name a value that can be written directly as:

```ocaml
let%hw some_signal = ...
```

If a value is assigned before it is ever used, it should usually just be defined directly instead of declared as a wire and assigned later.

In practice this means:

- RAM control signals like read addresses, write enables, write addresses, and write data should usually be plain `let%hw` values if they do not participate in a cycle.
- Keep only the genuinely cyclic or order-sensitive wires.

## Choose Control Logic and Timing Carefully

When implementing a circuit involving multiple interacting moving pieces, it is important to think carefully about what set of signals will control everything most straightforwardly, performantly, and elegantly.

For example, a module streaming a packet out of BRAM could use a `stream_start` and `stream_end` signal pulsing the cycle the stream starts/ends, or a single `streaming` signal that is high the entire time.
These signals could be aligned with the bytes streaming out of BRAM, or with the reads going into BRAM a cycle earlier.
While probably any combination of these could be the base of a working circuit, some could make the logic vastly simpler or more complicated, so think carefully and choose tastefully.

I recommend thinking of all the different signals you need to create (register enable/increment bits, output valid bits, etc.), as well as any other patterns like the above that could be useful, then determining the simplest ones which can easily be used to generate all the others.
In the above example, I'd probably have a start signal pulsing high the cycle before the first packet streams out, then another that stays high for the whole packet and is aligned with the BRAM output, but it depends on the specifics of the circuit.

Three miscellaneous hints:
- It's trivial to delay a control signal by a cycle with an inline `Types.Clocking.reg` (while going the other way requires making a completely different signal)
- ANDing level-triggered conditions about the state a circuit is in with various things which can happen (e.g., `processing_request &&: tag_match`) often makes logic simpler than alternatives
- Do not default to a full state machine with dedicated state enum, especially for simple transaction processing modules. A circuit with an state machine going between "IDLE", "PROCESSING", and "DONE" is almost never not the right way to go---there is probably a simpler solution that also avoids unnecessarily stalling input transactions in state DONE.

## Defining Record Types

When many related fields are stored or updated together throughout a module, define a custom record type that contains them.
For example, in a cache which must track the access currently being processed, we could create the following type:

```
module Active_access = struct
  type 'a t =
    { valid : 'a
    ; addr : 'a [@bits addr_width]
    ; load : 'a
    ; store : 'a
    ; store_data : 'a [@bits addr_width]
    ; tag : 'a [@bits bits_tag]
    ; index : 'a [@bits bits_index]
    ; word : 'a [@bits bits_word_index]
    ; base_addr : 'a [@bits addr_width]
    }
  [@@deriving hardcaml]
end
```

Notice that we include the `tag`, `index`, and `word` fields despite them being part of the `addr`, as well as a valid bit.
While we could store or compute these separately where needed, keeping them with the related fields is much cleaner.

## Helpers And Boundaries

Use helper functions when they isolate a distinct concern.

Good helper boundaries:

- Managing the streaming of a block of data one beat at a time.
- Converting a signal to a different format, such as an access size+offset to bytes with a mask.

Do not split out helpers for logic that is still tightly coupled to the top-level control decisions. If a helper mostly exists to hide complexity rather than isolate responsibility, it is probably the wrong boundary.

A good helper should have:

- A clear purpose.
- A small interface.
- Internal sequencing that is more understandable inside the helper than inline at the call site.

## RAM Structuring

For RAM-backed structures:

- Compute all read/write control signals first.
- Instantiate the RAMs after those signals are defined.
- Use wires for RAM outputs when those outputs are needed earlier in the file.

This usually produces a cleaner top-level shape, and is typically easier to read than interleaving RAM instantiations with control construction.

## Think Verbosely, Then Simplify

A recommended workflow is:

1. Work out the behavior in the clearest possible way, even if it is slightly verbose.
2. Identify which wires are only bookkeeping and which are truly necessary.
3. Replace transition-like logic with level-triggered conditions where possible.
4. Collapse derived signals into request records when that improves locality.
5. Only keep explicit state and wires that are still justified after simplification.

This repository values the cleaned-up final structure, but it is normal for intermediate design work to be more explicit while the hardware behavior is being understood.

## Final Check Before Committing

Before considering a Hardcaml implementation clean, check:

- Are named signals introduced with `let%hw` unless a wire is genuinely needed?
- Are registers created with `Types.Clocking.reg`?
- Are any wires declared only out of habit rather than necessity?
- Are there explicit state signals that can be replaced by direct conditions?
- Are helper modules isolating real concerns rather than just hiding complexity?
- Are derived request fields stored together in a record when widely reused?
- Does the control read like hardware behavior, not software bookkeeping?
